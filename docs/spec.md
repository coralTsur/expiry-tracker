# אפיון: מעקב אחרי פריטים עם תוקף (גרסה ראשונה)

## 1. הבעיה
אני מקבלת גיפטקארדים ולא שמה לב לתוקף, ואז הכסף "נזרק לפח". אותו דבר עם ביטוחים: לפני שביטוח רכב נגמר צריך זמן לסקר שוק, ולכן התראה מראש חשובה.

## 2. משתמשים
- משתמשת אחת (אני). אין התחברות בגרסה הראשונה.
- משתמשים נוספים יגיעו בהמשך (ראו חלק 6).

## 4. פעולות
- בתור משתמשת, אני רוצה להוסיף פריט, כדי שכל הפריטים עם תוקף יהיו במקום אחד ולא בקבוצת וואטסאפ.
- בתור משתמשת, אני רוצה לראות את כל הפריטים, כדי לדעת מה יש לי.
- בתור משתמשת, אני רוצה לעדכן פריט, כדי לתקן פרטים שהשתנו.
- בתור משתמשת, אני רוצה לעדכן סכום עדכני, כדי לדעת כמה נשאר בגיפטקארד שהשתמשתי בחלק ממנו.
- בתור משתמשת, אני רוצה לסמן פריט כמומש, כדי שלא יופיע יותר בתזכורות.
- בתור משתמשת, אני רוצה עמוד "פג בקרוב" עם הפריטים שתוקפם פג ב-30 הימים הקרובים, ממוינים לפי תאריך התוקף, כדי לא לפספס אף פריט.
- בתור משתמשת, אני רוצה למחוק פריט, כדי להסיר פריט שהוספתי בטעות.

## 5. כללים
- לא שומרים מספר כרטיס, קוד או CVV. רק שם ו-4 ספרות אחרונות.
- סכום עדכני לא יכול להיות גדול מהסכום המקורי. הכלל נבדק רק כששני הסכומים מולאו.
- תאריך תוקף חייב להיות עתידי (ממחר והלאה). בהוספה הכלל נבדק תמיד. בעדכון הוא נבדק רק אם תאריך התוקף השתנה, כך שאפשר לערוך פריט שתוקפו כבר פג (למשל לתקן את השם או לסמן כמומש) בלי לשנות את התאריך.
- אם התזכורת "כן", "ימים לפני התזכורת" חייב להיות קטן ממספר הימים שנשארו עד התוקף, כדי שהתזכורת באמת תגיע. הכלל חל בהוספה תמיד. בעדכון הוא נבדק רק אם אחד מהשדות `expirationDate`, `reminderEnabled` או `daysBeforeReminder` השתנה. עדכון של שדה אחר, למשל הסכום העדכני, לא נחסם בגלל הכלל הזה.
- פריט מומש לא מופיע בעמוד "פג בקרוב".
- פריט מופיע ב"פג בקרוב" אם הוא לא מומש, ותאריך התפוגה שלו בין היום ל-30 ימים מהיום (כולל). פריטים שתוקפם כבר פג לא מופיעים ברשימה הזו. הגדרות התזכורת (reminderEnabled, daysBeforeReminder) קובעות רק אם ומתי תישלח התראה.
- ברשימת כל הפריטים מופיעים כל הפריטים, כולל פריטים שתוקפם פג ופריטים שמומשו.
- כשיש שגיאה בטופס, הפריט לא נשמר, מוצגת הודעה ליד השדה הבעייתי, ושאר הפרטים שמולאו נשארים בטופס.

## 6. לא בגרסה הראשונה
- משתמשים נוספים: לכל משתמש תזכורות משלו, ואפשרות להיות שותף בתזכורת של מישהו אחר בהסכמתו (שיתוף קישור לפריטים).
- עמוד לניהול קטגוריות (בגרסה הראשונה הרשימה סגורה).
- הדבקת ההודעה שהתקבלה עם הגיפטקארד, ומילוי אוטומטי של כל הפרטים או חלקם (AI).
- התראות בטלגרם, במייל או בוואטסאפ (ייבחן לפי הקושי ואפשרויות החיבור).
- רשימה נפרדת של פריטים שתוקפם פג.

## 7. קריטריוני קבלה
- מוסיפה פריט בלי שם ← הודעת שגיאה ליד השדה, הפריט לא נשמר, שאר הפרטים נשארים בטופס.
- מוסיפה פריט בלי קטגוריה ← הודעת שגיאה ליד השדה, הפריט לא נשמר, שאר הפרטים נשארים בטופס.
- מוסיפה פריט עם תאריך תוקף שכבר עבר, או עם תאריך של היום ← הודעה "התאריך כבר עבר, אנא הזיני תאריך עתידי", הפריט לא נשמר, שאר הפרטים נשארים ואפשר לתקן רק את התאריך.
- מוסיפה פריט שפג בעוד 20 יום, עם תזכורת של 30 ← הודעת שגיאה ליד שדה התזכורת: "טווח התזכורת ארוך מהזמן שנשאר עד התוקף, אנא בחרי טווח קצר יותר", הפריט לא נשמר, שאר הפרטים נשארים ואפשר לשנות רק את טווח התזכורת.
- מעדכנת סכום עדכני גדול מהסכום המקורי ← הודעת שגיאה, השינוי לא נשמר.
- מעדכנת רק את הסכום העדכני בפריט שנשארו לו 20 יום ויש לו תזכורת של 30 ← השינוי נשמר.
- מעדכנת את השם של פריט שתוקפו פג ← השינוי נשמר.
- מסמנת פריט כמומש ← הפריט נעלם מ"פג בקרוב".
- מוחקת פריט ← הפריט לא מופיע יותר ברשימת כל הפריטים.

## 8. API

כל הנתיבים מתחילים ב-`/api/items`. גוף הבקשה והתשובה ב-JSON, ושמות השדות כמו בעמודה "שם בקוד" בחלק 3. תאריכים בפורמט `YYYY-MM-DD`.

### פעולות
| פעולה | Method ונתיב | גוף הבקשה | תשובה בהצלחה | שגיאות |
|---|---|---|---|---|
| כל הפריטים | `GET /api/items` | | 200, רשימת פריטים ממוינת לפי `expirationDate` (מהקרוב לרחוק) | |
| פריט אחד | `GET /api/items/{id}` | | 200, פריט | 404 |
| פג בקרוב | `GET /api/items/expiring-soon` | | 200, רשימת פריטים לפי הכלל בחלק 5, ממוינת לפי `expirationDate` | |
| הוספה | `POST /api/items` | פריט בלי `id` | 201, הפריט שנשמר כולל `id` | 400 |
| עדכון | `PUT /api/items/{id}` | פריט מלא בלי `id` | 200, הפריט אחרי העדכון | 400, 404 |
| סימון כמומש | `PATCH /api/items/{id}/redeem` | | 200, הפריט עם `redeemed: true` | 404 |
| מחיקה | `DELETE /api/items/{id}` | | 204, בלי גוף | 404 |

### פריט בתשובה
כל השדות מחלק 3, ובנוסף `id` (מספר שהשרת קובע). ה-`id` משמש את הצד הלקוח לזיהוי הפריט (למשל בכפתורי עריכה ומחיקה), ולא מוצג למשתמשת. דוגמה:
```json
{
  "id": 1,
  "category": "GIFT_CARD",
  "name": "BuyMe",
  "expirationDate": "2026-11-20",
  "amount": 200,
  "currentAmount": 150,
  "lastFourDigits": "1234",
  "acceptedStores": "Fox, Castro",
  "reminderEnabled": true,
  "daysBeforeReminder": 14,
  "redeemed": false
}
```

### פריט בבקשה (POST ו-PUT)
- אותם שדות, בלי `id`. ה-`id` מגיע מהנתיב או שהשרת קובע אותו.
- שדה רשות שלא נשלח נשמר ריק.
- `daysBeforeReminder` שלא נשלח מקבל 30.
- `redeemed` שלא נשלח: בהוספה הוא `false`, ובעדכון הוא נשאר כמו שהיה.
- ב-PUT שולחים את הפריט המלא, כמו שהטופס מציג אותו. שדה רשות שלא נשלח מתרוקן.

### שגיאות
גוף אחיד לכל השגיאות:
```json
{
  "status": 400,
  "error": "Bad Request",
  "message": "הפריט לא נשמר",
  "fieldErrors": {
    "expirationDate": "התאריך כבר עבר, אנא הזיני תאריך עתידי"
  }
}
```
- **400**: קלט שמפר כלל מחלק 5 או שדה חובה חסר. `fieldErrors` ממפה כל שדה בעייתי להודעה, כדי שהצד הלקוח יוכל להציג אותה ליד השדה (חלק 5). ההודעות בעברית, ובניסוח של קריטריוני הקבלה בחלק 7 כשקיים ניסוח כזה. אם יש כמה שגיאות, כולן מוחזרות יחד.
- **404**: אין פריט עם ה-`id` הזה. אין `fieldErrors`, וה-`message` מתאר את הבעיה, למשל "פריט 99 לא נמצא".
